3. 完整闭环：选择 → 执行 → 回传 → 作答
==============================================================
  用户问题: 贷款 100 万，年利率 5%，30 年，等额本息月供是多少？

  ① 模型决定调用: [('loan_monthly_payment', {'principal': 1000000, 'annual_rate': 5, 'years': 30})]
  ② 执行 loan_monthly_payment → 结果: 5368.22

  ③ 最终回答: 贷款 100 万元、年利率 5%、期限 30 年，按等额本息还款，**月供约为 5,368.22 元**。

下面补充几项参考数据：
- 累计还款总额约 1,932,559 元
- 其中利息总额约 932,559 元，接近本金的 93%

如需其他方案（比如 20 年、公积金利率、等额本金等），告诉我即可帮你算。

     问题 → 模型选工具 → 我们执行 → 结果回传 → 模型作答

4. 一次问多个 → 模型会并行调多个工具
==============================================================
  问题: 100摄氏度是多少华氏度？另外 2026-01-01 到 2026-03-01 有多少天？

  模型一次返回了 2 个工具调用：
    - convert_temperature({'value': 100, 'from_unit': 'C', 'to_unit': 'F'})  id=call_00_NnitqJV7...
    - days_between({'start_date': '2026-01-01', 'end_date': '2026-03-01'})  id=call_01_64YdPkPK...

  最终回答: 两个结果如下：

- **100 摄氏度 = 212 华氏度**（换算公式：F = C × 9/5 + 32）
- **2026-01-01 到 2026-03-01 相差 59 天**（2026 年不是闰年，1 月 31 天 + 2 月 28 天 = 59 天）

  >> 多个工具**互不依赖**时，模型会一次性全返回，
     我们可以并发执行（用线程池），不用一个个等。
     这点和 Java 里的 CompletableFuture.allOf 思路一致。

==============================================================
5. 逻辑公式类工具的设计原则
==============================================================
  ✅ 该做的：
   ① 幂等：同样的输入永远同样的输出（方便重试、缓存）
   ② 无副作用：不写库、不发消息、不改状态
   ③ 入参用基础类型，加默认值
   ④ 返回值说清楚单位（是元还是分？是摄氏度还是华氏度？）
   ⑤ 参数非法时返回**可读的错误说明**，让模型知道怎么改

  ❌ 不该做的：
   ① 别让模型传复杂结构（嵌套对象、数组能免则免）
   ② 别在工具里再调一次大模型（会指数级放大延迟和成本）
   ③ 别把业务规则写死在 prompt 里，应该写进工具代码
   ④ 别直接 eval 用户输入（安全问题，见 calc 里的注释）

  💡 一个很实用的判断标准：
     「这段代码如果写错了，是**逻辑错误**还是**算错**？」
       算错 → 做成工具（模型算不准）
       需要外部数据 → 做成远程调用工具（下一个文件）
       需要判断语义 → 别做工具，让模型自己来
