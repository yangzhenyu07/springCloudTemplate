5. 工具分组与路由判断（DeepSeek + 最新 API）
   注：本文件的「分组」是工具组织方式，不是 Skill —— Skill 标准见文件 7

==============================================================
1. 工具怎么分组（三种落地方式）
==============================================================
  ⚠️ 再次强调：这里的「分组」是**工具的组织方式**，不是 Skill。
     Skill 是标准格式（目录 + SKILL.md）→ 见 7.Skill标准规范与渐进式加载.py

  【方式一】平铺：全部塞进一个列表
     >>> tools = [t1, t2, t3, ...]
     优点：最简单。缺点：超过 20 个就管不住了，而且每次全发给模型。

  【方式二】BaseToolkit：官方提供的工具包抽象
     OrderToolkit().get_tools() → ['order_query', 'order_cancel', 'logistics_query']
     适合：要给某个工具包单独做安装/注册/权限控制

  【方式三】按业务域分字典（本文件的用法，推荐）
     【订单】['order_query', 'order_cancel', 'logistics_query']
     【商品】['product_search', 'product_stock', 'product_spec']
     【售后】['ticket_create', 'refund_policy']

     全部工具共 8 个，分 3 个域

  >> 分组的价值有两个：
     ① 管理：几十个工具不分组根本没法维护
     ② 路由：可以按域筛选，只把相关工具发给模型（省钱 + 提准，见 demo_7）

  >> 分域的一个副作用：**要自己维护一张反查表**
     TOOL_TO_DOMAIN = {工具名: 域名}，用来事后判断击中了谁。
     这是手工活，容易漏。如果你用标准 Skill（文件 7），
     工具的归属写在 SKILL.md 的 include_tools 里，不用另建表。

==============================================================
2. 【方法①】看 tool_calls —— 最直接
==============================================================
  Q: 我的订单 SO001 到哪了？
     → 击中工具: ['logistics_query']
     → 归属能力域: ['订单']

  Q: 你们这儿的键盘还有货吗？
     → 击中工具: ['product_search']
     → 归属能力域: ['商品']

  Q: 买了三天能退货吗？
     → 击中工具: ['refund_policy']
     → 归属能力域: ['售后']

  Q: 今天天气不错
     → 没击中任何域（直接回答）

  >> 这就是最基本的判断方式：
     tool_calls[i]['name'] → 查反查表 → 得到域名
     前提是你要自己维护一张「工具 → 域」的反查表。

3. 【方法②】回调 —— 全链路自动埋点
==============================================================
  用户: 查一下订单 SO001 物流，顺便看看键盘还有多少库存


  模型要求调用: ['logistics_query', 'product_search']

  执行工具（回调会自动记录）：
    [回调] on_tool_start: logistics_query → 属于【订单】
    [回调] on_tool_end: 返回 订单 SO001：已到达广州转运中心，预计明天送达
    [回调] on_tool_start: product_search → 属于【商品】
    [回调] on_tool_end: 返回 搜到 3 个与「键盘」相关商品：键盘 199、鼠标 99、显示器 899

  本次击中过的域: ['订单', '商品']

  >> 回调的好处：**不用改工具代码**，挂在 config 上就生效，
     还能自动传给子链（这是它比 with_listeners 强的地方，见 runnableModule/5）。

4. 【方法③】astream_events —— 适合流式推送给前端
==============================================================
  用户: 我想退货，买了三天了

  ① 只 bind_tools 不执行（很多人的第一反应）：
     事件类型: ['on_chat_model_end', 'on_chat_model_start', 'on_chat_model_stream']
     ↑ 没有 on_tool_*！因为 bind_tools 只让模型「说出想调谁」，
       真正执行是我们自己调 invoke() 才发生的，这一步不属于链。

  ② 把执行工具也放进链里（正确用法）：
    on_tool_start: refund_policy → 属于【售后】
       入参: {}
    on_tool_end  : 7 天无理由退货；已拆封商品需质量问题才能退；退款 3-5 个工作日到账

  ⚠️ 踩坑点（本节最重要的一条）：
     llm.bind_tools(...).astream_events() 只会有 on_chat_model_*，
     **不会有 on_tool_*** —— 因为工具压根没被执行。
     必须把「执行工具」这一步也接进链（RunnableLambda / ToolNode / agent），
     并且把 config 透传给 tool.ainvoke(...)。

  >> 适合做「进度提示」：
     前端可以显示「正在查询订单...」「正在查库存...」
     比回调更适合实时 UI。

5. 【方法④】工具内部埋点 —— 最可控
==============================================================
  在工具函数第一行写日志/埋点：
    @tool
    def tracked_order_query(order_no):
        hit_log.append({'domain': '订单', ...})   ← 就这一行
        return ...

  执行后埋点记录: [{'domain': '订单', 'tool': 'order_query', 'arg': 'SO002'}]

  >> 优缺点：
     ✅ 最可控，能记任意业务字段（用户 ID、耗时、结果码）
     ❌ 侵入工具代码，每个工具都要写一遍
     适合：需要业务级埋点/计费的场景

6. 【方法⑤】tool_choice 强制指定 —— 不靠模型选
==============================================================
  有时候你**不希望**模型自己选，比如：
    · 确定这一步必须查订单 → 强制调 order_query
    · 做信息抽取 → 强制它把抽取结果填进工具参数

  Q: 帮我把订单 SO003 取消了吧
     → 强制抽出: {'order_no': 'SO003', 'intent': '取消'}
  Q: SO004 到哪了？
     → 强制抽出: {'order_no': 'SO004', 'intent': '物流'}

  >> 这个技巧非常实用：**用工具调用做结构化抽取**。
     比让模型输出 JSON 再解析稳得多（schema 由 API 层保证）。
  ⚠️ DeepSeek 上必须关思考，否则 400。

7. 【方法⑥】自己做两级路由（最可控，推荐）
==============================================================
  问题：工具一多（比如 50 个），全塞给模型会：
    · 浪费 token（每次都要发 50 份说明书）
    · 准确率下降（选择太多，模型会犹豫）

  解法：**两级路由**
    第一级：让模型（可以用小模型）判断「属于哪个域」
    第二级：只把这个域的工具发给模型去选

  Q: 我的订单 SO001 到哪了？
     第一级路由 → 订单  （理由：用户在询问具体订单 SO001 的物流/配送进度，属于订单域。）
     第二级选工具 → 只从【订单】的 3 个工具里选 → ['logistics_query']

  Q: 键盘还有货吗？
     第一级路由 → 商品  （理由：询问键盘是否有库存，属于商品库存/商品信息查询，归入商品域。）
     第二级选工具 → 只从【商品】的 3 个工具里选 → ['product_search']

  Q: 买了三天能退吗？
     第一级路由 → 售后  （理由：用户询问购买三天后能否退货，属于退换货政策咨询，归入售后域。）
     第二级选工具 → 只从【售后】的 2 个工具里选 → ['refund_policy']

  Q: 你好呀
     第一级路由 → 无  （理由：只是打招呼，未涉及订单、商品或售后的具体诉求）
     第二级 → 无匹配域，直接回答

  >> 两级的收益：
     · token 省一大截（只发一个域的工具）
     · 准确率更高（选择范围小了）
     · 路由过程**可观测、可干预**（域判错了能人工兜底）
  ⚠️ 代价：多一次模型调用（第一级可以用便宜的小模型）
  ⚠️ DeepSeek 专属坑：with_structured_output 必须 method='function_calling'
     + 关思考，漏一个都是 400（详见上面代码注释）

8. 官方方案：LLMToolSelectorMiddleware
==============================================================
  langchain 1.4.7 自带了一个中间件，干的就是「先筛工具」这件事：

    LLMToolSelectorMiddleware
    参数: ['self', 'model', 'system_prompt', 'max_tools', 'always_include', 'max_retries', 'on_parsing_failure']

    用法：
      middleware = LLMToolSelectorMiddleware(max_tools=3)
      agent = create_agent(model=..., tools=50个工具, middleware=[middleware])

    作用：先用模型把 50 个工具筛到 3 个，再交给主模型
    （这其实就是上一节「两级路由」的官方实现——不用自己写）

    常用参数：
      max_tools       最多保留几个工具
      model           用哪个模型筛选（可以指定小模型省钱）
      always_include  永远保留的工具（比如查用户信息）

    ⚠️ DeepSeek 上直接用会 400（内部走 json_schema）。
       绕过方案见 6.Agent与工具实战.py 的 demo_5（自定义 ChatOpenAI 子类）。

9. 六种判断方式怎么选
==============================================================
  方式                    成本          可控性     什么时候用
  ----------------------------------------------------------------------------
  ① 看 tool_calls        零成本         低       调试、简单场景
  ② 回调                  零成本         中       全链路自动埋点、计费
  ③ astream_events      零成本         中       流式 UI、进度提示
  ④ 工具内埋点               改代码         高       业务级埋点、需要业务字段
  ⑤ tool_choice 强制      零成本         最高      确定必须调某个时
  ⑥ 两级路由                多一次调用       最高      工具多（>20）时

  💡 我的建议（实用排序）：
     工具 < 10 个     → 平铺 + 看 tool_calls 就够了
     工具 10~30 个    → 按域分组 + 回调埋点
     工具 > 30 个     → 两级路由 / LLMToolSelectorMiddleware
     要 100% 可控     → tool_choice 强制指定

  ⚠️ 三条经验：
   ① 工具描述**划清边界**（写明「不适用于...」）比什么都重要
   ② 名字要有区分度，别都叫 query_xxx
   ③ 路由判断一定要**留日志**，否则出问题无从查起

  【什么时候该升级到标准 Skill（文件 7）】
     如果除了工具，你还想给模型**配套的说明文档、脚本、参考资料**，
     或者希望「工具 + 知识」一起按需加载 → 那就别用本文件的分组了，
     改用标准 Skill：目录 + SKILL.md，配置 include_tools 绑工具。
     好处：工具的归属写在 SKILL.md 里，不用自己维护反查表。
