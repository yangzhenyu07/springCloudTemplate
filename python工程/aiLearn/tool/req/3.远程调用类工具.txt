1. 为什么远程工具必须设超时
==============================================================
  ❌ 反面教材：requests.get(url) 不设 timeout
     Python 的 requests **默认没有超时**！
     对端不响应 → 这个请求会一直挂着 → 整个链路卡死
     在高并发服务里，几个这样的请求就能拖垮整个线程池。

  ✅ 正确写法：requests.get(url, timeout=5)
     超时后抛 requests.Timeout，我们捕获后返回错误信息给模型。

  实测两种写法（用一个**故意延迟 10 秒**的 URL）：

  【不设超时】——为了不真卡死，这里只演示 5 秒就放弃观察：
    requests.get('https://httpbin.org/delay/10')  → 会一直等到对端响应（可能永远）
    ⚠️ 不实际执行，否则脚本会卡住

  【设 2 秒超时】真实执行：
    requests.Timeout —— 耗时 3.03s 后放弃 ✅

  >> 经验值：内部服务 2~5 秒，第三方 5~10 秒，
     并且一定要小于整个链路的超时时间。

2. 错误分类：哪些该重试，哪些不该
==============================================================
  错误类型              重试？                 原因
  ------------------------------------------------------------------------
  超时 Timeout        ✅ 该重试               可能是网络抖动或对端临时慢
  5xx 服务端错误         ✅ 该重试               对端挂了，可能马上恢复
  429 限流            ✅ 该重试（要退避）          退避等待后再试
  4xx 客户端错误         ❌ 别重试               参数错了，重试一万次也错
  401/403 鉴权        ❌ 别重试               权限问题，重试没用
  DNS 失败            ❌ 别重试               地址写错了

    "Accept": "*/*",

    客户端 404      → 请求失败（客户端错误 404）：地址可能不对，请换个 URL
    服务端 500      → 远程调用失败，已重试 1 次。最后错误：服务端错误 500

  >> 关键设计：把「错误信息」当成字符串返回给模型，
     而不是抛异常终止链路。模型看到错误会自己换个参数重试。

4. ⚠️ 安全：凭据绝不能当工具参数
==============================================================
  ❌ 危险写法：把 api_key 做成工具参数
     @tool
     def query_order(order_no: str, api_key: str) -> str: ...
     问题：
       · api_key 会出现在发给模型的 JSON Schema 里（泄露给模型厂商）
       · 模型可能「幻觉」出一个假的 key
       · 对话日志里会留下明文凭据

  ✅ 正确写法：凭据从**环境/配置**注入，不进 schema
     schema 字段: ['order_no']
     → 模型只看到 order_no，看不到任何凭据 ✅
     调用结果: 订单 SO20261028001：已发货（用 key=demo*** 查询）

  还有一条：**用户输入不要直接拼进 URL / SQL**。
     ❌ f'SELECT * FROM orders WHERE no={order_no}'   → SQL 注入
     ✅ 用参数化查询 / URL 编码

5. 远程调用类工具的设计清单
==============================================================
  项             重要度       说明
  ------------------------------------------------------------------
  设超时           必须        不设会拖垮整个服务
  错误分类          必须        4xx 不重试，5xx/超时才重试
  重试 + 退避       必须        退避避免重试风暴
  降级方案          建议        挂了返回兜底值，别让整轮对话失败
  结果裁剪          必须        别把整个 HTML 塞回给模型，浪费 token
  缓存            建议        相同查询缓存几秒，省钱又提速
  超时日志          必须        否则「为什么变慢」查不出来
  幂等            看情况       写操作要保证重复执行不出问题
  凭据隔离          必须        不进 schema，从配置注入

  ⚠️ 最容易被忽略的一条：**结果裁剪**
     远程接口经常返回一大坨 JSON/HTML，
     全塞回给模型 = 白花 token + 干扰模型判断。
     正确做法是只挑**需要的字段**再回传。

  💡 一个实用模式：工具里再包一层「精简函数」
     原始响应 → 提取关键字段 → 转成简短文本 → 回传模型
