1. 工具的三种定义方式（无需 API key，纯本地）

==============================================================
1. 方式一：@tool 装饰器（最常用）
==============================================================
  定义：
    @tool
    def add(a: int, b: int) -> int:
        '''计算两个数的和。'''
        return a + b

  LangChain 自动从函数里抽出了三样东西：
    ① name        = add
    ② description = 计算两个数的和。

    当遇到加法、求和、相加等需求时使用这个工具。
    ③ args_schema = ['a', 'b']

  调用方式（三种等价）：
    add.invoke({'a': 3, 'b': 5})      → 8
    add.run({'a': 3, 'b': 5})         → 8
    add.func(3, 5)  (原始函数)          → 8

  ⚠️ 注意：@tool 装饰之后，add 已经**不是原来的函数**了，
     它是一个 BaseTool 对象。想拿原函数用 add.func。
     （Java 视角：被代理对象包了一层，直接调用行为变了）

  >> 小知识：docstring 的**第一行**是简述，后面是详细说明，
     两者拼起来都会给模型。所以第一行写清干什么，后面写什么时候用。

==============================================================
2. 方式二：StructuredTool.from_function
==============================================================
  用 from_function 显式指定三要素：
    name        = query_weather
    description = 查询指定城市的当前天气。用户问天气、气温、要不要带伞时用。
    args_schema = ['city', 'unit']

  调用: 广州：晴，26摄氏度
  带单位: 广州：晴，26华氏度

  生成的 JSON Schema（这就是发给模型的「接口文档」）：
    city: 城市名，例如：广州、北京。不要带「市」字以外的修饰
    unit: 温度单位：摄氏度 或 华氏度

  >> 什么时候用这种方式：
     · 想让工具名和函数名不一样
     · 想给参数加详细约束（Field(description=...)、默认值）
     · 工具是**运行时动态生成**的（比如从数据库读配置造一批工具）

==============================================================
3. 方式三：BaseTool 子类（完全可控）
==============================================================
    name        = query_price
    description = 查询商品价格。问「多少钱」「价格」「报价」时使用。
    同步调用    : 键盘 的价格是 100 元
    VIP 价      : 键盘 的价格是 80 元
    异步调用    : 鼠标 的价格是 100 元

  必须实现的：**_run**（可选：**_arun**）
  ⚠️ 坑：方法名写错成 run / execute 不会报错，但调用时报 NotImplementedError。

==============================================================
4. 异常处理：ToolException 是干什么的
==============================================================
  普通异常 vs ToolException：

    · 普通 Exception  → 整个链路崩掉，调用方收到异常
    · ToolException   → 可以被「捕获」成一条消息回传给模型

  实测：直接 invoke 抛 ToolException：
    ToolException: 除数不能为 0，请换一个非零的除数

  如果想让它变成「回传给模型的消息」，要这样构造工具：
    handle_tool_error=True → invoke 返回: '除数不能为 0，请换一个非零的除数'

  >> 生产建议：工具内部**自己消化**可预期的错误，
     返回「出错原因」字符串让模型重试，比直接抛异常更稳。

==============================================================
5. description 怎么写（最重要的一节）
==============================================================
  description 是模型判断「用不用这个工具」的**唯一依据**。

  ❌ 反面例子：
    name=search  description=搜索
    → 模型不知道什么时候该调它，也不知道不该调它

  ✅ 正面例子：
    name=search_product_doc
    description=在【产品文档库】中检索相关内容。当用户询问产品功能、使用方法、参数配置、报错含义时使用。不适用于：订单查询、物流查询（那些有专门的工具）。输入是检索关键词，不是完整句子。

  写 description 的四要素（记住这个模板）：
    ① 干什么       → 「在【产品文档库】中检索相关内容」
    ② 什么时候用   → 「当用户询问产品功能、使用方法...时使用」
    ③ 什么时候别用 → 「不适用于：订单查询、物流查询」
    ④ 参数怎么给   → 「输入是检索关键词，不是完整句子」

  ⚠️ 第③条「什么时候别用」最容易被忽略，但**最有用**：
     工具一多，描述重叠，模型就会乱选。显式划清边界能大幅提升准确率。

  另外：name 也要起得有区分度。
     ❌ search / query / get      → 十几个工具都这么叫，模型分不清
     ✅ search_product_doc / query_order_status

==============================================================
6. 三种方式怎么选
==============================================================
  方式                              代码量     可控性     什么时候用
  ------------------------------------------------------------------------------
  @tool                           最少      低       90% 的日常场景
  StructuredTool.from_function    中等      中       要指定 schema / 动态造工具
  BaseTool 子类                     最多      高       要异步、有状态、自定义异常处理

  还有两个实用变体：
    · create_retriever_tool(检索器, 名字, 描述)  → 把 RAG 检索器变成工具
    · convert_runnable_to_tool(链)               → 把一条 LCEL 链变成工具

  ⚠️ 通用注意事项：
    ① 参数尽量用**基础类型**（str/int/bool/float/枚举），别塞复杂对象
    ② 参数能设默认值就设，减少模型填错的几率
    ③ 返回值尽量是**字符串或可序列化对象**，模型要读得懂
    ④ 耗时长的工具要设超时，否则整个链路挂住
