  >> 注意：拿到的是 pydantic 对象，可以直接 .entities 取字典，
     不用 json.loads，也不用担心模型多输出了别的话。
     这就是 with_structured_output 的价值（详见 outputParser/3）。

2. ⚠️ 增量更新的坑：自由 key 下同覆盖根本不生效
==============================================================
  第 1 轮抽到: ['yangzhenyu']
          实体库现在 1 个:
            yangzhenyu: 用户的名字；住在广州
  第 2 轮抽到: ['Java', 'Spring Boot']
          实体库现在 3 个:
            yangzhenyu: 用户的名字；住在广州
            Java: 用户有 9 年 Java 经验
            Spring Boot: 用户最喜欢的框架
  第 3 轮抽到: ['深圳']
          实体库现在 4 个:
            yangzhenyu: 用户的名字；住在广州
            Java: 用户有 9 年 Java 经验
            Spring Boot: 用户最喜欢的框架
            深圳: 用户搬家后现居住地

  ⚠️ 实测发现的坑：我原本以为「广州」会被「深圳」覆盖，
     但结果是**两个都在**——模型把「搬家」抽成了新实体「深圳」，
     而不是把「广州」的值更新掉。

  原因：实体名（dict 的 key）是**模型自由发挥**的，
     它可能写「居住地」「城市」「广州」「深圳」…… 每次都不一样。
     所以「同名覆盖」这个机制在自由 key 下**经常失效**。

  怎么修（三种办法，按推荐度排序）：
   ① 【最推荐】固定字段：别用 Dict[str,str]，改成固定的 pydantic 字段
      class Profile(BaseModel):
          name: str | None
          city: str | None
          years_of_java: int | None
      → key 由你定，更新一定生效
   ② 给抽取 prompt 明确列出「允许的实体名清单」
   ③ 抽完做一次归一化/实体链接（把「广州」「深圳」都归到 city 字段）

  【用办法①实测一次】固定字段 schema：
    「我叫yangzhenyu，住在广州」 → {'name': 'yangzhenyu', 'city': '广州', 'main_language': ''}
    「我有 9 年 Java 经验」 → {'name': 'yangzhenyu', 'city': '广州', 'main_language': ''}
    「我搬家了，现在住在深圳」 → {'name': 'yangzhenyu', 'city': '深圳', 'main_language': ''}

  >> 看最后的 city：广州 → 深圳，**真的更新了**。
     这就是固定字段比自由 Dict 可靠的原因：key 由你控制。

3. 实战：实体记忆 + 对话链
==============================================================
  第 1 轮  Q: 我叫yangzhenyu，住在广州
          A: 好的，已记住你叫yangzhenyu，住在广州。
          实体库: 2 个 → ['yangzhenyu', '广州']
  第 2 轮  Q: 我有 9 年 Java 经验，最喜欢的框架是 Spring Boot
          A: 好的，已记住：9年Java经验，最爱Spring Boot。
          实体库: 4 个 → ['yangzhenyu', '广州', 'Java', 'Spring Boot']
  第 3 轮  Q: 我最近在学 LangChain
          A: 好的，知道了：你在学 LangChain。
          实体库: 5 个 → ['yangzhenyu', '广州', 'Java', 'Spring Boot', 'LangChain']

  最终实体库：
   - yangzhenyu: 用户的名字；住在广州
   - 广州: yangzhenyu居住的城市
   - Java: 用户有9年经验
   - Spring Boot: 用户最喜欢的框架
   - LangChain: 用户最近在学 LangChain

  【关键验证】清空对话历史，只靠实体库回答：
   A: 你叫杨振宇，住广州，有9年Java经验。

  >> 即使历史全清空，只要实体库在，模型依然答得出来。
     这就是实体记忆最强的地方：**记忆独立于对话历史**，
     换会话、换设备、跨天，实体库还在（只要持久化了）。

4. 三种记忆横向对比
==============================================================
  维度        缓冲/裁剪             摘要记忆              实体记忆
  --------------------------------------------------------------
  存什么       对话原文              一段摘要文本            结构化 KV
  额外成本      无                 压缩时 1 次调用         每轮 1 次调用
  老信息       超限就丢              保留但可能失真           精确保留
  可查询       ❌                 ❌                 ✅ 直接查 key
  省 token   最费                中等                最省
  实现复杂度     最简单               中等                最复杂

  什么时候用实体记忆：
   ✅ 客服/陪聊：要记住用户的姓名、偏好、订单号
   ✅ 长期陪伴类产品：跨会话记住用户画像
   ✅ 信息密度高、且需要精确查询的场景

  什么时候别用：
   ❌ 闲聊（没实体可抽，白花钱）
   ❌ 对成本敏感（每轮多一次调用，token 翻倍）
   ❌ 对话逻辑本身很重要（实体存不下「怎么说的」）

  生产建议：
   · 抽取和对话**并行**做，别串行等（用 RunnableParallel，见 runnable/1）
   · 实体库持久化到 Redis/DB，key 带上 user_id
   · 给实体数量设上限，防止有人恶意刷
   · 敏感信息（手机号、身份证）**不要**存进实体库
