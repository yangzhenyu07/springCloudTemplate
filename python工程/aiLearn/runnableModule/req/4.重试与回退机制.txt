==============================================================
1. with_retry：失败了自动重试
==============================================================
  失败 2 次后成功，设置 stop_after_attempt=3：

    第 1 次调用... 失败
    第 2 次调用... 失败
    第 3 次调用... 成功
   结果: 成功：hello

  --------------------------------------------------------

  失败 5 次，但只让重试 3 次：

    第 1 次调用... 失败
    第 2 次调用... 失败
    第 3 次调用... 失败
   最终抛出: ConnectionError: 模拟网络抖动

  >> stop_after_attempt = **总尝试次数**（含第一次），不是「额外重试几次」。
     写 3 = 最多跑 3 次 = 失败 2 次后第 3 次成功。

==============================================================
2. ⚠️ 关键参数：只重试该重试的异常
==============================================================
  默认行为是「任何异常都重试」——这在 LLM 场景很危险。
  比如参数写错导致的 400，重试 3 次就是白花 3 倍的钱。

  【默认】ValueError 也会被重试（❌ 不应该）：
    最终抛出: 参数错误：model 不存在
    → 白跑了 3 次（参数错误重试 3 次纯属浪费）

  【限定 retry_if_exception_type=(ConnectionError,)】
    参数错误（ValueError）会**立刻**抛出，不重试：
    最终抛出: 参数错误：model 不存在
    → 只跑了 1 次 ✅

  验证 ConnectionError 时确实重试了：
    → ConnectionError 一共跑了 3 次 ✅

  生产建议的可重试异常：
    · 网络类：ConnectionError / Timeout / socket.timeout
    · 限流类：HTTP 429（RateLimitError）
    · 服务端：HTTP 500 / 502 / 503
  不该重试：
    · HTTP 400 参数错误（重试也没用）
    · HTTP 401 鉴权失败（重试也没用）
    · 自己代码的逻辑错误

==============================================================
3. 重试间隔：退避 + 抖动
==============================================================
  with_retry 默认就开了 **指数退避 + 抖动**（wait_exponential_jitter=True）。
  意思是：第 1 次失败等一会儿，第 2 次等更久，且加随机量。

  为什么要「抖动(jitter)」？
    如果 1000 个请求同时失败、同时重试，会形成**重试风暴**，
    把刚恢复的服务再次打垮。加随机量能把重试时间打散。

  实测：失败 2 次后成功，总耗时 3.43s（含退避等待）
        尝试了 3 次

  参数说明：
    wait_exponential_jitter   默认 True，指数退避 + 随机抖动
    exponential_jitter_params 可以细调（initial/max/jitter/exp_base）
    stop_after_attempt        总尝试次数（含第一次）

  ⚠️ 注意：退避等待是**同步阻塞**的，
     在高并发服务里要算好它对线程池的占用。

4. with_fallbacks：主组件挂了自动换备用
==============================================================
  【函数版】主函数必失败，看会不会切到备用：

    主组件：执行中...    备用组件：执行中...    备用结果

  >> 机制：按顺序试，第一个成功的就用，全失败才抛异常。

  【实战】主模型用了不存在的模型名，自动切到备用模型：

    结果: Redis 是一个开源的高性能内存键值数据库，常用于缓存、消息队列和实时数据处理等场景。
    耗时: 1.27s（先试主模型失败，再试备用）

  >> 这就是教材里「切换为不存在的模型引发出错 → 回退」的写法。
     生产上典型用法：
       · 主用贵的强模型，挂了切便宜的
       · 主用自家部署，挂了切公有云
       · 主用国外模型，被墙/超时切国内模型

5. 多个备用 + exception_key
==============================================================
  fallback 可以是一串，按顺序依次尝试：

    A 失败
    B 失败
    C 失败
    最后备用成功
    终于成功了

  --------------------------------------------------------

  exception_key：想知道「到底为什么失败」时用

  先试传字符串（会报错）：
    ❌ ValueError: If 'exception_key' is specified then input must be a dictionary.However found a type of <c

  改成传 dict：
    抱歉，服务暂时不可用（原因：原始错误信息）

  >> exception_key 实测总结（两点都不太直观）：
     ① 开了它，输入**必须是 dict**，传字符串直接 ValueError
     ② 兜底函数收到的是「原始输入 + exception 键」组成的 dict，
        不是单独的异常对象，要自己 .get('exception') 取出来

6. 组合使用 + 怎么选
==============================================================
  【组合】先重试几次，都不行再回退：

    主组件第 1 次，失败
    主组件第 2 次，失败
    主组件第 3 次，失败
    主组件第 4 次，成功
    主组件结果

  顺序很重要：
    with_retry 包在里面  → 先重试，重试完还失败才回退  ✅ 正确
    with_fallbacks 包在里面 → 每次失败立刻回退，重试没机会  ❌

--------------------------------------------------------------
  选型表：

    方式                干什么                   什么时候用             注意
    ----------------------------------------------------------------------------
    with_retry        同一个东西再试几次             偶发抖动、限流           限定异常类型
    with_fallbacks    换一个东西                 组件彻底不可用           备用组件要真的能兜住
    二者组合              先重试再换                 生产标准做法            注意嵌套顺序

  ⚠️ 三条生产经验：
   ① 重试一定要配 retry_if_exception_type，别啥都重试
   ② 要设总超时，否则重试 + 退避可能让请求挂很久
   ③ 回退链路也要打日志，否则「为什么变慢了」查不出来
