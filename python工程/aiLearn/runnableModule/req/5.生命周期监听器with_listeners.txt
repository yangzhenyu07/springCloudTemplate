5. with_listeners 生命周期监听器（DeepSeek + 最新 API）

==============================================================
1. 最小示例：on_start / on_end / on_error
==============================================================
  正常执行：
    ▶ on_start  name=RunnableLambda
    ■ on_end    name=RunnableLambda

  抛异常时（只有 on_start 和 on_error 会触发）：
    ▶ on_start  name=boom
    ✖ on_error  name=boom
    （异常向外抛出: 故意失败）

  >> 注意：on_error 触发后，异常**照样会往外抛**，
     listener 只是「通知」，不会吞掉异常。要吞就得用 with_fallbacks。

==============================================================
2. Run 对象和 config 里到底有什么
==============================================================
  【Run 对象】常用字段：
    id          : 01a18647-5f2d-7d91-b6ce-8855d0a2da30
    name        : RunnableLambda
    run_type    : chain
    start_time  : 2026-10-29 06:09:46.796542+00:00
    inputs      : {'input': 'hello'}
    （outputs/end_time 在 on_end 里才有）

  【config 对象】常用字段：
    configurable: {'user': 'yangzhenyu'}
    tags        : ['demo']
    metadata    : {}
    callbacks   : None

  >> 最有价值的是 config['configurable']：
     业务参数（user_id / trace_id）都从这里取，listener 里能做审计日志。

  【on_end 里】outputs={'output': 42} / end_time 有值=True

3. 实战：监控某个组件的耗时
==============================================================
  执行整条链：
    [步骤1-检索] 耗时 0.30s
    [步骤2-生成] 耗时 0.00s
    答案：问题 资料

  >> 这是 listener 最典型的用途：**单独盯住某一步的耗时**。
     用回调也能做，但要在 on_chain_start 里判断 name，写起来更绕。

==============================================================
4. ⚠️ 关键区别：只管自己，不传给子链
==============================================================
  挂在整条链上，看触发几次：
    ▶ on_start: RunnableSequence
    → on_start 触发了 1 次

  再把 listener 挂到**内层组件**上：
    ▶ on_start: RunnableLambda
    → on_start 触发了 1 次（只有内层的那一次）

  ⚠️ 对比一下回调：
     callback 绑在顶层，**会**自动传给所有子链
     listener 绑在哪，就**只**盯那一个 Runnable

  >> 所以：
     要全链路追踪 → 用回调（callable 组）
     要盯某一步   → 用 listener

5. 实战：给模型调用加审计日志
==============================================================
  调用一次带审计的模型：
    Redis 是一个开源的、基于内存的高性能键值数据库，常用于缓存、消息队列和实时数据处理。

  审计日志：
    {'event': 'start', 'ts': 1793254187.2159843}
    {'event': 'end', 'ts': 1793254190.0890384, 'outputs_type': 'dict'}

    本次耗时约 2.87s

  >> 生产上可以把这个换成写 Kafka / 日志文件 / 监控系统。
     注意 listener 里别做太重的操作，会拖慢主流程。

==============================================================
6. 什么时候用 listener
==============================================================
  适合：
   · 盯某个具体组件的耗时 / 成功率
   · 某一步执行完要发个通知（比如检索完成推进度）
   · 针对某一步做审计日志
   · 某一步失败要告警（但不想吞异常）

  不适合：
   · 全链路追踪        → 用回调或 LangSmith
   · 想吞掉异常        → 用 with_fallbacks（第 4 个文件）
   · 想重试            → 用 with_retry（第 4 个文件）

  ⚠️ 三个注意事项：
   ① listener 里抛异常会**中断主流程**，务必自己 try/except
   ② listener 是同步执行的，别在里面做重 IO（会拖慢链路）
   ③ on_error 触发后异常仍会向外抛，listener 不是 try/catch

  和回调的对照：

    维度        with_listeners        BaseCallbackHandler
    --------------------------------------------------------
    作用范围      某一个 Runnable          整条链 + 所有子链
    写法        传三个函数                 继承类 + 重写方法
    传递性       ❌ 不传递                 ✅ 自动传给子链
    典型用途      盯某一步                  全链路日志/追踪/计费
